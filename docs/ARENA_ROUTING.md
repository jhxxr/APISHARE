# 真实榜单辅助自动路由

公开排行和自动路由共用每日同步到本地的 Arena 官方历史快照，但**公开分数、任务策略和渠道指标分开保存**。请求处理只读本地数据，不拉外部榜单，也不额外调用模型试算。

## 开关与上线方式

站点与私人路由均有 `arena_mode`：

| 模式 | 实际转发 |
| --- | --- |
| `live`（默认，缺少该字段的旧配置同样使用此模式） | 使用 Arena 辅助的新策略，无须先观察 |
| `shadow`（可选调试） | 使用旧启发式统一池排序；另存 Arena 建议，便于对照 |
| `off` | 仅旧策略 |

它独立于站点路由原有的 `mode`。站点整体仍为 `shadow` 时，实际转发依然遵守原先的默认模型规则；开启 Arena 不会绕过整体影子模式。

观察不是启用前置条件。旧配置明确保存的 `shadow` / `off` 会保留，可随时在设置中改为 `live`；不会静默覆盖操作者的显式选择。观察模式不执行建议模型，因此没有“建议模型的实际延迟、实际费用或回答正确率”；这些不能从对照日志中凭空推算。

## 统一候选池（替代旧四档优先级）

- 已移除手动 SIMPLE / MEDIUM / COMPLEX / REASONING 候选表、列表优先级及逐档顺延。站点与个人路由都只使用 `model_pool`（留空自动使用所有已绑定且有权限的模型），并应用 `excluded_models`。
- 旧 `tiers` 中的模型与 `model_pool` 合并、去重、稳定排序后迁入统一池；保留 `model(high,128k)` 等显式变体，不保留原档位和排列优先级。保存后旧档位列表为空；老客户端发送的档位也只当作待合并模型集合。
- 请求难度标签只决定任务质量门槛与自动思考强度，不再把模型分成不可跨越的候选档位。不同源榜分数仍不混加。
- 未知型号无虚构分数：正式模式无可信数据时优先显式兜底，否则按模型标识稳定排序，这不是能力排名。渠道的优先级、权重与故障转移机制保持不变。

## 选择流程

1. 沿用既有权限、额度、协议、模态、上下文及健康检查，只对已准入候选排序。
2. 根据任务主领域选一个分榜：前端选 WebDev；Agent 任务选 Agent；视觉选 Vision；文档 / 长文本可参考 Document；其余选 Text。代码、数学和通用长文本会标明弱参考，**不把 Text 或 Document 当成 SWE、数学或极限上下文专项成绩**。
3. 首选分榜没有可信匹配时可退到 Text，明确标注 `general_reference_only`。不同分榜的 Arena Rating 与 Agent IPS 不相加、不做固定权重合成。
4. 按以下可审查的候选政策分组，再使用质量 / 成本 / 延迟偏好选首项。
5. 同组首项失败时优先尝试剩余参考分较高的候选。保留进行中的会话亲和性，不保留手动档位边界。

既有上下文压缩 / 可用性最后兜底规则保留；未通过预检而进入这类单一兜底的项不会被套上榜单评分，也不会被新策略重新包装成合格候选。

### 初始候选政策（不是准确率承诺）

- 最少 **100 个源榜样本**，发布及获取时间均不超过 **7 天**；日期异常、过期、缺样本时不作为可信质量依据。
- 简单任务：非 `quality_first` 策略允许选择源榜样本充足模型的中位数以上候选。
- 中等任务：对应门槛为全榜上四分位数。
- 复杂任务、推理任务及 `quality_first`：以领先候选及其区间为参考。区间组以单个领先项为锚，避免区间重叠链把明显较弱模型串进同组；区间重叠只是一项候选政策，不等于统计显著性检验。
- 站内没有达到政策门槛的模型时使用可信的最佳可用候选，或明确配置的兜底；无数据的型号保持未知，不凭 `pro/max/mini` 名称补能力分。

以上是首版运行政策，观察对照和真实任务回归后才能验证是否适合本站负载；不能把榜单分位解释为任务成功率。

## 版本与渠道

### 公开接入标记与路由评分是两种匹配

- 公开排行的“本站已接入”按产品型号/日期版本匹配，可忽略明确的 `(High)`、`(Max)`、`(Thinking)` 等测试思考强度。它表示本站有这一型号，不保证实际请求复现榜单测试配置；源榜名称、分数和名次不改写。
- 自动路由的实测评分证据仍精确核对实际思考配置，不共享上述宽松匹配；不同日期、Pro/Mini、Preview 等产品区别也不能被抹去。下述专门的新版本先验必须另行标记为推断。
- 没有对应版本记录的本站模型单列展示，不补排名、不套旧版本分数。模型别名以实际映射为准；不公开未发布的内部部署标识。
- DeepSeek 官方文档在 2026-11-11 核验：2026-10-17 将 `deepseek-flash` 升为 **V4.1-Flash-1017**，官方兼容别名也转到该版本。只对 `https://api.deepseek.com` 的已核验别名做公开版本标注，第三方同名渠道不继承这项承诺。
- 本次读取的 2026-11-09 Text 快照仍包含 `DeepSeek-V4.1-Flash-20260910 (Max)`，不能把它标成 1017 的成绩。对应行提示“本站版本不同”，1017 接入信息出现在未匹配版本列表；只有源榜真正出现 1017 时才标记到对应行。

官方版本依据：[DeepSeek 模型与定价说明](https://api-docs.deepseek.com/quick_start/pricing)。

### 新版参考旧版：0910 → 1017 的显式政策

按本站策略，新版尚未收录时可参考旧版，并略优先新版。目前仅为 DeepSeek V4.1 Flash 的 2026-09-10 → 2026-10-17 设置该规则，其他型号和版本不自动类推。

- 明确带 `1017` / `20261017` 的型号，或已核验官方 API 的滚动别名，可使用本地同分榜旧 0910 版本的成绩作为暂定质量先验；不修改实际发送给上游的模型 ID。
- 优先找相同思考配置；缺失时采用旧版已收录配置中分数最低且样本充足的条目，明确记录思考配置未经验证。过期、少样本、重复歧义、混合版本渠道仍不可套用。
- 原始分数、区间、名次和样本均保留为**旧版证据**，不造“新版分数”。在分数与来源相同时略优先新版，不跳过任何更高实测分；已知成本/延迟偏好、服务稳定性和会话规则仍适用。
- 日志和试算使用 `status=version_reference`、`version_reference=true`、`version_reference_note`、`reference_thinking_unverified`，显示“旧版参考／新版推断”，不是 `matched` 实测。此推断不能开启“更强实测模型”的语义探针。
- 对应分榜一旦出现 1017 实测结果（即使比旧版更低），停止这条旧版推断；实际请求配置有精确匹配时使用新成绩，否则保持配置未知。
- 公开官方榜单完全不加分、不补名次；未匹配的 1017 接入信息仍单独列示。观察模式只记录推断建议，不改变实际转发。

- 按实际上游模型映射和解析后的思考配置匹配；不把默认、High、None 或不同日期版本混用。
- 固定 token budget 不擅自等同某个 High 档。一个别名可能转到不同型号、或源榜存在无法区分的同名条目时，不挑最高分套用。
- 主要渠道池的服务成功率只代表服务稳定性，响应时间只代表观测延迟。普通客户端 4xx、请求参数校验和语义拒答不计入新服务窗口；服务侧超时、中断或未能完成约定协议格式则可计为服务失败。真实评分始终保留原值，不由 HTTP 200、Beta 后验或拒答次数加减。
- 延迟仅在主要池都有观测时比较；持续失败的主要渠道可被降序，但备用渠道的失败不冒充主要渠道故障。个人统计不借用站点或其他用户记录。
- 渠道降序使用独立的传输 EWMA，而非带旧能力先验的 Beta 参数；每个主要渠道至少 5 次观测且加权近期服务成功 EWMA 低于 50% 才触发。10 分钟无传输观测后失效并在下次调用重置，避免很久以前的故障永久饿死模型。运行内样本计数不是严格的“最近 10 分钟请求量”。
- 当前渠道观测来自启用表现记录的自动路由调用；未经过该路径的直接模型调用不会自动补成这些样本。缺数据保持未知，不主动多调用模型测速。
- 语义探针只在下一个候选有可信、更高的同一分榜评分时启用，不把“更弱备选”称为升档。

工具数量上限属于渠道/端点的请求兼容性约束。遇到明确的顶层 `tools` 数量超限时，保留完整工具和 `tool_choice`，先尝试同模型的其他渠道，再沿自动模型候选链兜底；不重试已拒绝的渠道，不据此扣减服务或能力表现。全部渠道不兼容时返回 400，并说明客户端与最终上游工具数量（包括适配器追加项）。不会擅自截断工具列表；用户需要减少启用的 MCP/工具或使用能容纳该工具数量的渠道。

## 成本与速度

- `quality_first`：优先原始质量参考。
- `cost_first`：在可接受组中比较已知费用；未知单价不等于免费，显式零价可用。
- `latency_first`：在可接受组中比较有观测的主要渠道响应时间。流式首个输出与非流式完整响应分开观测，不把 HTTP 响应头延迟当成首字；未知速度不从模型名称推断。历史值不保证下一次请求（输出长度、思考预算等可能不同）的延迟。
- `balanced`：先求费用 / 延迟的非支配候选，再考虑暖会话（估算至少 3000 token）的缓存亲和性与质量参考；不拼接 Elo、IPS、美元和 HTTP 成功率生成一个伪“能力总分”。

费用字段是**比较参考**：估算输入 token 加用户明确的输出上限；未提供输出上限时使用 1024 输出 token 作为比较基准并记录该值，不声称这是实际生成量。没有证据时不预设 Prompt Cache 折扣。BYOK 账单不等于本站单价，因此保持费用未知。

比较费用不代表额外重试、探针或失败后再次发送上下文的总成本；实际账单和失败兜底开销需单独观察。

## 对照与可解释日志

`billing.router.arena` 包含策略模式、分榜 / 配置、源榜发布日期、弱参考标记、候选门槛、原候选、建议候选、实际转发及变更原因。`steps[].arena` 保留原始排名 / 分数 / 区间 / 样本、匹配状态、渠道样本和比较费用依据。

实际运行失败换候选时只更新 `actual_model`，不改写原始建议。调试响应头可查看 `X-APISHARE-Router-Arena-Mode`、`-Board` 和 `-Different`。

判断效果应分别看真实任务质量回归、实际账单费用、首字与总耗时、服务失败率、兜底率、数据匹配覆盖率，不能只看“HTTP 成功率变高”。
